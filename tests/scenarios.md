# Evaluation cases

These are regression prompts and expected behavior, not claims of a measured model-quality benchmark.

## Critic

1. A provided designed ad for a mostly 65+ audience: select five voices including one wildcard, inspect the actual image at realistic size, tie findings to visible elements. Readability can outweigh a critic's aesthetic preference. Do not promise sales lift.
2. A request to review an inaccessible ad: state the limitation; no invented visual observations. Ask for accessible content if necessary.
3. A specified cast of three: honor exactly three, overriding default five and wildcard quota.
4. A Rick-only personal uncertainty: load mirror only; 1–3 grounded sentences, no fabricated psychological certainty.
5. A dense chart: prefer evidence and information expertise; do not force all favorites into the cast or delete useful density.
6. A native ad with no boxed CTA: judge against its actual brief; do not prescribe a button by default.
7. “Destroy this”: blunt specific criticism without personal abuse or invented defects.
8. Baldwin reviewing copy: identify a concrete evasion or abstraction; avoid a generic sermon and present the lens as interpretation.

## Next Feature

1. Prototype with no users: inspect existing functionality, propose a concrete capability provisionally; do not invent customer demand.
2. “Give me five ideas”: provide five, with a short plan for the best unless all plans requested.
3. Annual export needed for a real workflow: consider value despite low frequency and an existing manual workaround.
4. “Improve engagement”: translate to an explicit trigger, user action and result; confirm it does not already exist.
5. Named implementation request: respect that authorization; planning-only defaults do not cancel it.
6. Missing product identity: ask one necessary question rather than invent the product.
7. Existing capability discovered: don't recommend rebuilding it; find the evidenced gap or say no build is justified.
8. A bug blocks the core task: label a repair as a repair rather than pretending it is a new feature.

Structural validation and manual walkthroughs are initial checks. Future quality comparisons should run the same fixtures with the same model/settings, assess grounded specificity and usefulness blind, and record actual input/output tokens and latency.
